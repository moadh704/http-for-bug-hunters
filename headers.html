Module 03

Headers

Headers decide who the request is for, whether it is cached, and which origin may read the response. Most HTTP bugs are header bugs.

Host is routing

Host (or the :authority pseudo-header) picks the site on a shared IP. If the app uses that value to build a password-reset link, a cache key, or an absolute redirect, you can sometimes aim that link at a host you control. That is host-header injection. Test it only on a lab or a program that allows it.

X-Forwarded-Host and X-Forwarded-For are claims made by the previous hop. They are trustworthy only if the app knows that hop is its own proxy. An app that believes a client-supplied forwarded host is making the same mistake.

Identity rides in two places

Cookie is the browser's ambient credential. Authorization is an explicit one, often a bearer token. A bug that reflects a cookie into HTML is different from a bug that reflects a token. Note which one the app actually checks, and whether a request with neither still returns private JSON.

Set-Cookie flags are part of the finding when they are wrong: missing Secure, missing HttpOnly on a session, or a Domain that covers every subdomain.

Cache and CORS

A shared cache stores a response when it thinks the request is public. Vary tells it which request headers change the body. If a personalized page is stored without Vary: Cookie, the next visitor receives someone else's page. That is cache deception or poisoning depending on who controls the key.

Access-Control-Allow-Origin echoes a request's Origin, and Access-Control-Allow-Credentials is true, only when the server meant that exact site to read credentialed responses. A reflected star, or a reflected origin plus credentials, is the bug. A star alone cannot be used with credentials.

Read the response headers on a request that included an Origin you do not own. The interesting part is whether the server copies it.

Headers worth naming

    Check yourself

    Three questions. Nothing unlocks. A pass is just a mark in this browser so you know you read it.

    1. Why is a client-supplied X-Forwarded-Host dangerous?

      Forwarded headers are only meaningful from a proxy the app trusts. From the client they are just another header.

    2. A personalized response stored by a shared cache is unsafe when

      Vary (and private Cache-Control) exist so one user's response is not replayed to another.

    3. Access-Control-Allow-Origin: * together with credentials

      Browsers refuse to expose a credentialed response when the allowed origin is a star. A reflected specific origin plus credentials is the real bug.
